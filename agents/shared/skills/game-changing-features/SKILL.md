# Game-changing features

Product strategy with a founder's mentality. Not "what's next on the backlog" — what would
make users unable to live without this?

Pure strategy: no implementation, no code changes. And **no spec files** — the analysis goes
in the conversation. Only write it to a file when the user asks, where they say.

## 1. Understand the value that exists

Before proposing anything, read the product. Run searches and reads in the current worktree;
don't reason from the conversation alone.

- What problem does this solve today, and for whom?
- What's the core action users take, and where do they spend their time?
- What do they complain about or request most?

## 2. Find the opportunities, at three scales

**Massive** — expands what the product can do. New markets, new use cases.
- What adjacent problem would make this indispensable?
- What turns this from a tool into a platform?
- What would make a competitor nervous?

**Medium** — force multipliers on what already works.
- What makes the core action 10x faster or easier?
- What data do we already hold and not use?
- What painful manual workflow could be automated?

**Small** — low effort, disproportionate value. The easiest to overlook.
- What one shortcut saves minutes a day?
- What are users hunting for that we could just surface?
- What anxiety could one indicator eliminate?

Force yourself through every category — Speed · Automation · Intelligence · Integration ·
Collaboration · Personalization · Visibility · Confidence · Delight · Access — rather than
stopping at the first few good ideas.

## 3. Evaluate ruthlessly

Score each idea on: **impact** (how much more valuable), **reach** (what share of users),
**frequency** (how often they hit the value), **differentiation** (sets us apart or just
matches), **defensibility** (copyable, or compounds), **feasibility** (can we build it).

Verdict per idea: **Must do** · **Strong** · **Maybe** · **Pass**.

## 4. Stack rank

Don't hand back a list — hand back an order.

- **Do now** — quick wins with outsized impact; ship fast, validate fast.
- **Do next** — high leverage, moderate effort.
- **Explore** — strategic bets: name the risk and the upside.
- **Backlog** — good, but say why not now.

## Output

Lead with the recommendation, then the reasoning. Per idea: what it is, why it's 10x rather
than 10%, what it unlocks, rough effort, verdict. Drop any section with nothing real in it —
no empty headings. End with the open questions that need the user's input, and the
assumptions worth validating before anyone builds.

## Rules

- **Think big first** — capture the idea, evaluate it later; don't self-censor with "too hard".
- **Small can be huge** — one button sometimes changes everything.
- **User value, not feature count** — ten features at 1% each ≠ one that adds 10x.
- **Be specific** — "better UX" is not an idea; "one-click rescheduling from the notification" is.
- **Question assumptions** — "users want X" may be wrong. What do they actually need?
- **Prefer compounding** — features that get more valuable over time build moats.
- **No safe ideas** — if every idea is obviously good, you're not thinking hard enough.
- **Cite evidence** — point at the file, the data, or the research behind a claim.

## When stuck

- What would make a user tell a colleague about this?
- What's mildly annoying every single day?
- What would we build with 10x the team? With a tenth?
- What would a competitor have to build to beat us?
- What do power users do by hand that could be native?
- What do we know from the data that users never see?
- What sounds crazy but might work?
